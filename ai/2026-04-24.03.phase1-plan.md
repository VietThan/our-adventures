# Plan: Phase 1 MVP slice for our-adventures

**Date:** 2026-04-24
**Status:** Planned
**Depends on:** `2026-04-11.00.our-adventures-plan.md`, `2026-04-24.00.phase0-completion-log.md`

---

## Why this phase exists

Phase 0 is effectively complete: the repo exists, local Postgres exists, infra exists, deployment exists, DNS/TLS exists, and the app is reachable in production.

What does **not** exist yet is the first real product slice:

- the homepage is still scaffold copy
- API routes are placeholders
- query functions are not implemented
- there is no seeded baseline import path
- there is no authenticated end-to-end user flow

Phase 1 should convert the project from "deployed scaffold" into "usable private MVP."

---

## Current state summary

Grounded in the repo as it exists on 2026-04-24:

- `apps/web/src/app/page.tsx` is still a scaffold landing page
- `apps/web/src/app/api/activities/*`, `/api/me`, and `/api/activities/pick` are placeholder handlers
- `apps/web/src/db/queries/index.ts` is empty
- Google auth config exists in `apps/web/src/lib/auth.ts`, but it uses `next-auth` v4 and an `ALLOWED_EMAILS` env var allowlist
- `db/migrations/001_initial_schema.sql` exists, but it does not include the `link` field present in `data/activities.json`
- `apps/web/src/types/activity.ts` includes `link`, so the data contract is currently inconsistent
- `README.md` and some older planning docs still describe a more scaffolded or different state than the repo now has

This means Phase 1 is not just feature work. It also needs a short contract-alignment pass so the implementation does not harden the wrong assumptions.

---

## Phase 1 goal

Deliver a private, authenticated MVP where Viet and Linh can sign in, see the seeded activity catalog, filter by category, open an activity, mark it done for themselves, and get a random undone pick.

That is the first point where the product is materially better than the original single-file prototype because the shared backend, persistence, and per-user state are real.

---

## User-visible outcomes

By the end of Phase 1:

- both allowed users can sign in with Google in production
- the app loads real activities from Postgres
- the baseline 400 activities can be imported into a fresh environment
- a signed-in user can view activity lists and a single activity detail
- a signed-in user can mark an activity complete for themselves
- a signed-in user can request a random undone activity
- basic UI exists for these flows, even if it is still visually simple

## Decisions locked so far

These decisions have already been made and should be treated as Phase 1 scope:

- auth should move to Auth.js v5 early in Phase 1
- the allowlist should be database-backed, not env-driven
- the `users` table should be adjusted so email is the allowlist key and Google identity attaches after first login
- the two allowed users should be seeded as part of bootstrap
- user seeding should be idempotent
- the 400 baseline activities should be treated as a one-time bootstrap import, not an ongoing sync contract
- Postgres should generate durable activity IDs
- the database becomes the authoritative catalog after import; JSON regeneration can be handled later as a DB-to-file export concern
- activity editing is out of scope for Phase 1 and moves to Phase 2
- ratings are out of scope for Phase 1 and move to Phase 2
- the UI should be mostly server-rendered with only small client interactivity where needed
- route handlers remain the main backend contract; no server-action-first design
- custom activity create/update/delete stays out of Phase 1
- activity responses should expose both Viet and Linh completion state
- completion timestamps should be included
- the main list should show shared status at a glance
- the default browsing scope should be `undone by me`, with `all` as an explicit filter
- category filtering and status-scope filtering should both be visible on the main page
- the random picker should respect active filters
- when the filtered picker pool is empty, the UI should offer an explicit fallback to pick from all undone
- category selection in Phase 1 should use simple buttons/tabs, not the wheel UI
- signed-out users should see a small landing screen rather than a hard auth gate
- that landing screen should stay minimal and functional in Phase 1
- the signed-in experience should be a single-page dashboard, not split across multiple product pages
- activity detail should open inline on the dashboard, not via a dedicated page-first flow
- on desktop, detail should use a side panel; on mobile, a stacked/full-width section
- completion should be available directly from list rows and also from the detail panel
- in the default `undone by me` view, completed rows should disappear immediately after success
- `link` should remain part of the Phase 1 contract and be added to the DB schema
- shared status should use stable actual names, not `You` / other-user relabeling
- shared status in Phase 1 should stay text/icon-only, with no avatar UI
- completion timestamps should appear in the detail panel, not inline in list rows
- list rows should use compact shared-status markers rather than repeating names on every row
- the main list should use stable ordering, with `id ASC` as the Phase 1 default
- category filters should use plain labels in Phase 1, not counts
- the status-scope control should use buttons/tabs, not a checkbox/toggle
- Phase 1 should only support `undone by me` and `all`, not a separate `completed by me` scope
- the random picker should return an inline suggestion/detail experience, not a modal
- picker results should auto-select immediately
- picker results should replace any current selection immediately
- picker selection should not also auto-scroll/highlight the row in the list
- Phase 1 should include search
- search should match title plus notes/tip text
- search should submit on enter/button, not live-update on every keystroke
- search/category/scope should live in the URL query string
- the selected activity should also live in the URL as dashboard state
- if a selected activity does not match the current filters, the dashboard should still open its detail panel and surface the mismatch explicitly
- if a selected activity is completed and drops out of the default list, the detail panel should stay open with a clear mismatch notice rather than closing or auto-advancing
- when a selected activity does not match current filters, the UI should offer a one-click action to switch filters so it appears in the list
- list shared-status UI should use compact per-user columns/markers under stable `Viet` and `Linh` headers
- the Phase 1 detail panel should include title, category, season, notes, tip, link, both users' status/timestamp, and the complete / uncomplete action
- search UI copy should stay literal: placeholder `Search title, notes, or tips`, button `Search`
- the main empty state should offer clear recovery actions such as clearing search and switching to `All`
- picker fallback copy should be explicit and inline: `No matching undone activities.` plus a `Pick from all undone` action
- auth failure states should use short explicit messages for blocked email and conflicting Google account binding
- bootstrap should ship as a manual script under a repo-level `scripts/` directory and be documented rather than hidden in ad-hoc operator notes
- Phase 1 docs updates should explicitly include `README.md` and `db/README.md` in addition to the planning docs

## Workstreams

### 1. Contract alignment

Resolve repo drift before broad feature work:

- migrate from `next-auth` v4 to Auth.js v5 so the implementation matches the intended App Router pattern
- replace the env-var allowlist with a database-backed allowlist
- adjust the `users` contract so pre-seeded allowed users can exist before first Google login
- add the missing `link` column to the DB contract so the existing dataset is preserved
- update stale docs so Phase 1 work is building on the actual system, not the April 11 assumptions

This should be treated as Phase 1 entry criteria. The rest of the phase depends on these contracts being stable.

### 2. Database access layer

Implement the real query layer in `apps/web/src/db/queries/`:

- list activities with optional category filter
- fetch a single activity
- fetch current-user completion state
- mark completion
- remove completion
- random undone activity for current user
- upsert local app user record on first successful authenticated request

The query layer should stay thin and explicit. Raw `pg` is already the chosen approach.

### 3. Seed/bootstrap path

Create one reliable import path for `data/activities.json`:

- runnable against local Docker Postgres
- runnable against production by operator or deploy step
- idempotent for the two allowed user rows
- one-time/fresh-db-only for the baseline activity catalog

Without this, the MVP cannot be reproduced in a new environment.

### 4. Authenticated route handlers

Replace placeholder handlers with real behavior:

- `GET /api/me`
- `GET /api/activities`
- `GET /api/activities/:id`
- `POST /api/activities/:id/complete`
- `DELETE /api/activities/:id/complete`
- `GET /api/activities/pick`

Custom activity create/update/delete can wait unless implementation falls out cheaply from the same query layer.

### 5. First usable UI

Build the minimum UI needed to exercise the MVP:

- minimal signed-out landing screen with sign-in entry
- signed-in single-page dashboard
- visible category and status-scope filters on the main page
- simple search UI that submits through URL state
- category-based activity list, defaulting to `undone by me`
- shared completion status indicators for both users on list rows using compact markers
- inline activity detail
- detail panel remains openable even when the selected item does not match current filters
- when selected detail falls out of the visible list, the panel stays open and offers a one-click filter-recovery action
- complete / uncomplete action from both list rows and the detail panel
- random pick interaction that respects active filters
- explicit fallback when filtered random-pick has no matching undone rows

The Phase 1 UI does not need the full category wheel, rating UI, avatar UI, activity editing, or the final visual language from `nyc-adventure`. It does need to prove the backend contract and core workflow.

### 6. Verification and operability

Add enough validation that Phase 1 can be changed safely:

- route-level request validation with `zod`
- basic happy-path manual test checklist for local and production
- at least minimal automated coverage where it is cheap and stable
- updated setup docs for local boot, seed import, auth env vars, and deploy expectations
- explicit bootstrap/runbook docs in `README.md` and `db/README.md`

---

## Recommended sequencing

1. Align the contracts: auth version, allowlist approach, `link` field, stale docs.
2. Implement user bootstrap plus one-time activity import so the app has real data and a real allowlist.
3. Build the query layer and `GET /api/me`.
4. Build read flows: list, detail, random pick.
5. Build write flow: complete / uncomplete.
6. Replace the scaffold homepage with a simple authenticated product UI.
7. Verify locally, then verify on the deployed environment.

This sequence keeps the first vertical slice narrow and avoids building UI on top of placeholder or drifting contracts.

## Out of scope for Phase 1

These should stay out unless they become trivial:

- full parity with every `nyc-adventure` interaction pattern
- polished category wheel UI
- activity ratings
- avatar-heavy shared-presence UI
- edit/create/delete custom activities
- editing baseline activities
- shared live presence or real-time push updates
- admin tooling
- deep test infrastructure or broad integration coverage
- infra redesign

Phase 1 is about getting the first durable product loop working end to end.

## Risks and decisions to make early

### Auth version drift

The app currently uses `next-auth` v4 while Phase 1 now intends to standardize on Auth.js v5. Migration needs to happen early, before route and UI work spread the old pattern further.

### User contract correction

The earlier plan modeled `users.id` as Google `sub`. That does not fit a DB-backed allowlist with pre-seeded users. Phase 1 should correct this before login logic is implemented deeply.

### Data contract drift

The seed data and TypeScript types include `link`, while the SQL schema does not. Phase 1 now explicitly keeps `link`, so the schema must be updated before bootstrap/import work proceeds.

### False sense of completeness

Some project docs now say Phase 1 is in progress or imply more implementation than exists. Phase 1 should end with an accurate README and plan set so future work starts from reality.

## Definition of done

Phase 1 is complete when all of the following are true:

- a fresh local environment can start Postgres, apply schema, import baseline activities, and run the app
- a fresh local environment can also seed the two allowed users idempotently
- an allowed Google user can sign in and receive a working session via the database-backed allowlist
- the homepage/dashboard displays real activities from the database
- category filtering, search, and `undone by me` / `all` filtering all work via URL state
- a signed-in user can view a single activity and both users' completion states with timestamps
- the list shows compact shared-status markers for both users at a glance under stable named headers
- a signed-in user can complete and uncomplete an activity
- completed rows disappear immediately from the default `undone by me` list
- a signed-in user can get a random undone activity within the active filters
- when no filtered undone activity exists, the UI offers an explicit fallback to pick from all undone
- picker results auto-select into the inline detail view
- the dashboard can still open a selected activity from the URL even when it does not match the visible filters
- when selected detail no longer matches visible filters, the UI offers a one-click filter recovery path
- production has been exercised successfully with the same core flow
- README, `db/README.md`, and relevant planning docs reflect the actual post-Phase-1 system
