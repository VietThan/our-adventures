# Plan: Phase 2 product completeness for our-adventures

**Date:** 2026-04-25
**Status:** Draft
**Depends on:** `2026-04-24.03.phase1-plan.md`

---

## Why this phase exists

Phase 1 made the full-stack product loop real: authenticated users can browse the
seeded catalog, filter it, open details, complete/uncomplete activities, and use
the picker. Phase 2 should make the app feel like the original `nyc-adventure`
prototype again, while keeping the backend-owned shared state that Phase 1 added.

The key product tension:

- `our-adventures` is now more correct: database persistence, shared completion
  state, private Google auth, production deploys.
- `nyc-adventure` still has the better product feel: a strong two-panel layout,
  category wheel, visible stats, quick add/edit/delete, ratings, season tags,
  and a more decisive surprise picker.

Phase 2 should close that product gap without reopening foundation work.

## Product decisions

### Custom activity ownership

Use a numeric app-user foreign key for new custom activity ownership.

Recommended migration:

```sql
ALTER TABLE our_adventures.activities
  ADD COLUMN IF NOT EXISTS added_by_user_id BIGINT
    REFERENCES our_adventures.users(id);

CREATE INDEX IF NOT EXISTS activities_added_by_user_id_idx
  ON our_adventures.activities (added_by_user_id);
```

Keep the existing `added_by TEXT` column as a legacy/deprecated field for now.
The original `added_by` shape came from the early Google-sub model; Phase 1
changed users to numeric IDs, so Phase 2 should not build new ownership checks on
that text field.

Baseline activities should have `is_custom = false` and `added_by_user_id IS
NULL`. New activities should have `is_custom = true` and `added_by_user_id =
currentUser.id`.

Edit/delete rule for Phase 2:

- seeded baseline activities: not editable or deletable
- custom activities: editable/deletable by the creator
- optional stretch: allow either user to edit custom activities, but only if the
  UI communicates shared ownership clearly

Default recommendation: creator-only edits/deletes. It is stricter and easier to
reason about.

### Ratings and reviews

Use the existing `completions.rating` and `completions.review` columns.

The three completion verbs have distinct, non-overlapping responsibilities:

- **`POST /api/activities/:id/complete`** — initial completion only. Inserts the
  row with `completed_at = NOW()`. On conflict (already complete), does nothing —
  `ON CONFLICT DO NOTHING`. Does not accept or apply `rating`/`review`. This
  preserves the original `completed_at` if the user calls POST again.
- **`PUT /api/activities/:id/complete`** — updates `rating` and/or `review` on an
  existing completion row. Does not touch `completed_at`. Accepts optional
  `rating` (integer 1–5) and `review` (trimmed text, nullable). Returns 404 if
  the row does not exist (user has not completed the activity yet).
- **`DELETE /api/activities/:id/complete`** — uncompletes and clears
  `rating`/`review`.

The UI should allow:

- complete now without rating
- set/change rating after completion via PUT
- add/edit a short review after completion via PUT
- clear rating/review when uncompleted

### Filtering

Phase 2 should extend filtering to:

- completion scope: `undone`, `done`, `all`
- category
- season: `any`, `spring`, `summer`, `fall`, `winter`
- search

Unlike Phase 1, `done` should become a first-class scope. This mirrors the
prototype category filters and supports ratings/history work.

The scope type stays `"undone" | "done" | "all"` and the URL param value stays
`scope=undone`. Display labels use "To do" / "Done" / "All" in the UI. This
avoids a breaking change to any existing bookmarked URLs and keeps the parser
change minimal (just add `"done"` as a recognized value).

URL state should remain the source of truth for filters and selection.

### Visual direction

Use `nyc-adventure` as the main UI reference, but adapt it to the shared backend:

- desktop: sticky left navigation panel with title, stats, category wheel,
  picker, and add action
- desktop: right panel for the active category/list/detail workflow
- mobile: compact top category selector or horizontally scrollable wheel
  alternative; do not force the full radial wheel into cramped viewports
- keep category colors varied and stable
- use season badges with distinct seasonal colors
- use tasteful completion celebration on the toggle button, but only after a
  successful server write — this belongs in Slice 2 when the completion flow is
  being touched for ratings, not deferred to the visual pass

The visual style should feel like a working personal tool, not a marketing page.

## Workstreams

### 1. Data contract and query layer

Add the backend shape needed for Phase 2 before UI work spreads assumptions:

- migration for `activities.added_by_user_id`
- expose `isCustom` and owner in activity types/responses
- expose `rating` and `review` in completion status types/responses
- add query functions for:
  - create custom activity
  - update custom activity
  - delete custom activity
  - complete with optional rating/review
  - update rating/review on an existing completion
  - stats summary for current user and both users
- extend list query filters with `season` and `scope = todo | done | all`

Implementation guidance:

- Keep raw `pg` and explicit SQL.
- Keep route handlers as the backend contract.
- Validate request bodies with `zod`.
- Use transactions for update/delete paths that need ownership checks plus a
  write.

### 2. Custom activity CRUD

Implement end-to-end custom activities:

- `POST /api/activities`
- `PUT /api/activities/:id`
- `DELETE /api/activities/:id`
- modal or side-panel form with:
  - title
  - category
  - notes
  - tip
  - link
  - season
- list/detail affordances:
  - show add button near the main navigation
  - show edit/delete only for custom activities the current user can manage
  - clearly distinguish custom activities from seeded activities, but subtly

Definition of done:

- a user can create an activity and immediately see it in the current category
- a user can edit their custom activity without changing its ID or completion
  data
- deleting a custom activity removes its completions through cascade
- seeded activities do not show edit/delete controls
- unauthorized edit/delete attempts return 403 or 404 without changing data

### 3. Ratings, reviews, and completion history

Bring back the most useful part of the prototype's completed-item experience:

- star rating UI on completed activities
- optional short review field in the detail panel
- completion date remains visible
- completed category/list views should sort recent completions first
- rating updates should not reset `completed_at`
- uncomplete should clear rating/review unless a future product decision says
  memories should be preserved

Definition of done:

- a user can complete without rating
- a user can rate 1-5 after completion
- a user can edit or clear their rating/review
- the other user's rating/review can be visible in detail, but not editable
- API validation rejects invalid ratings

### 4. Browsing, stats, and picker

Make browsing feel closer to the prototype:

- category wheel or wheel-inspired selector
- left-panel stats:
  - total activities
  - current user's done count
  - current user's remaining count
  - done by both
- category subtitle:
  - todo count
  - done count
  - optional done-by-both count
- scope filters: `All`, `To do`, `Done`
- season filter using badges or segmented controls
- picker result as a focused overlay or prominent panel with:
  - "tonight, let's..."
  - category badge
  - title
  - notes
  - tip
  - link when present
  - pick again
  - mark done

The picker should respect active category/season/scope where that makes sense.
If scope is `done`, picker should default back to todo/undone candidates rather
than suggesting already-completed activities.

### 5. Responsive visual polish

Port the useful design structure, not the exact implementation:

- define shared category metadata in TypeScript:
  - label
  - color
  - order
- use that metadata across filters, rows, detail, picker, and stats
- replace generic category pills with the new navigation treatment
- keep the row density closer to the prototype than the current card-heavy list
- keep detail content scannable: notes, tip, link, shared status, ratings
- verify desktop and mobile layouts with screenshots before calling Phase 2 done

Responsive expectations:

- desktop: two-panel layout is the primary experience
- tablet: navigation can remain visible but compact
- mobile: category selector becomes horizontal/compact; details stack below list
- controls must not overflow or cover content

### 6. Tests and verification

Add targeted coverage around the new shared-data risk:

- unit or integration tests for filter parsing, especially season/scope
- query tests where cheap against local Postgres scripts, or route-level tests if
  the project adds a test runner
- manual checklist for:
  - create/edit/delete custom activity
  - creator-only ownership enforcement
  - complete/rate/review/uncomplete
  - both-user visibility
  - picker with category and season filters
  - mobile layout

Do not build a broad test framework before the first Phase 2 slice. Add the
smallest stable test setup that protects the new write paths.

## Recommended sequencing

### Slice 1 - custom activity CRUD

Do this first because it completes the biggest missing product promise from the
original app and exercises the ownership model.

Deliverables:

- `003_custom_activity_owner.sql`
- types/query updates for custom activity fields
- `POST /api/activities`
- `PUT /api/activities/:id`
- `DELETE /api/activities/:id`
- add/edit form UI
- creator-only controls
- lint/build verification

### Slice 2 - ratings and reviews

Do this second because the DB columns already exist and it improves the emotional
value of completed activities.

Deliverables:

- `POST /complete` changed to `ON CONFLICT DO NOTHING` (preserves `completed_at`)
- `PUT /api/activities/:id/complete` added for rating/review updates
- detail panel rating/review UI
- completed views show stars and completion date
- completion celebration on successful `POST` write
- invalid ratings rejected

### Slice 3 - season and done browsing

Do this before the major visual pass so the new navigation has the right states.

Deliverables:

- `scope = undone | done | all` (URL param stays `scope=undone`; labels are "To do" / "Done" / "All")
- season filter in URL state
- list query supports season and done scope
- completed views sort by recent completion
- empty states updated

### Slice 4 - `nyc-adventure`-inspired visual system

Do this after the product state is complete enough to design around.

Deliverables:

- category metadata module
- desktop two-panel layout
- category wheel or wheel-inspired selector
- stats panel (required: total / done-by-me / remaining / done-by-both — implement as a query in the page layer or `GET /api/stats`)
- stronger picker result treatment
- mobile-responsive fallback for wheel/navigation

### Slice 5 - targeted tests and docs

Do this as the closeout pass.

Deliverables:

- focused tests for new write paths/filter parsing, if practical
- manual verification checklist
- README updates for Phase 2 behavior
- production smoke check after deploy

## API target

Phase 2 should move the API surface closer to the original long-term plan:

| Method | Path | Phase 2 behavior |
|---|---|---|
| `GET` | `/api/activities` | List with category, season, scope, search |
| `POST` | `/api/activities` | Create custom activity |
| `GET` | `/api/activities/:id` | Get detail with statuses, ratings, owner/custom flags |
| `PUT` | `/api/activities/:id` | Update owned custom activity |
| `DELETE` | `/api/activities/:id` | Delete owned custom activity |
| `POST` | `/api/activities/:id/complete` | Initial completion; `ON CONFLICT DO NOTHING` — never resets `completed_at` |
| `PUT` | `/api/activities/:id/complete` | Update `rating`/`review` on existing completion; 404 if not yet complete |
| `DELETE` | `/api/activities/:id/complete` | Uncomplete and clear rating/review |
| `GET` | `/api/activities/pick` | Pick from active category/season filters |
| `GET` | `/api/me` | Current user profile |
| `GET` | `/api/stats` | Dashboard stats (required by Slice 4; can live in page query layer instead of a separate route) |

## Open decisions

1. Should custom activities be editable only by the creator, or by either
   allowed user?

   Recommendation: creator-only in Phase 2.

2. Should uncompleting preserve a user's old rating/review as a memory?

   Recommendation: clear rating/review on uncomplete in Phase 2. Preserve richer
   memory history for a later phase.

3. Should the category wheel be a true radial wheel on desktop?

   Recommendation: yes on desktop if implementation stays contained; use a
   simpler horizontal selector on mobile.

4. Should picker results appear in an overlay like the prototype or stay inline?

   Recommendation: use a focused overlay or modal-like panel for picker results.
   The prototype's picker feels more decisive because it interrupts browsing and
   gives one answer.

5. Should baseline activities become editable later?

   Recommendation: not in Phase 2. Add custom activities first, then decide
   whether seeded catalog corrections need a separate admin/editing model.

---

## Definition of done

Phase 2 is complete when:

- users can create, edit, and delete custom activities
- baseline activities are protected from edit/delete in UI and API
- custom activity ownership is enforced server-side
- users can complete, rate, review, update, and uncomplete their own completion
- ratings/reviews are visible in activity detail
- category, season, search, and todo/done/all filters work through URL state
- dashboard stats show meaningful totals for the current user and shared progress
- the main dashboard visibly borrows the stronger structure of `nyc-adventure`
  without losing responsive behavior
- picker results feel focused and support picking again
- lint and production build pass
- production smoke test covers browse, custom create, complete/rate, picker, and
  delete custom activity
