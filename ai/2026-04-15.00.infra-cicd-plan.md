## Part 1: `infra/` CDK skeleton

### Overview

`infra/` owns only the EC2 compute layer. VPC, RDS, and security controls live in `shared-aws-infra` (already deployed). This CDK project reads their outputs from SSM at deploy time — it does not import or reference the `shared-aws-infra` CDK app directly.

One stack: `ComputeStack`.

### `infra/lib/compute-stack.ts`

This is the most detailed file. All SSM parameter names below are exact names confirmed from the deployed stacks.

#### SSM reads at synth time

CDK reads SSM plain strings at synthesis using `ssm.StringParameter.valueFromLookup()`. These are looked up once during `cdk synth`/`cdk deploy` and baked into the CloudFormation template. Do not use `valueFromLookup` for secrets.

```typescript
const vpcId      = ssm.StringParameter.valueFromLookup(this, '/shared/network/vpc-id');
const appTierSgId = ssm.StringParameter.valueFromLookup(this, '/shared/network/app-tier-sg-id');
const oidcArn    = ssm.StringParameter.valueFromLookup(this, '/shared/iam/github-oidc-provider-arn');
```

These three SSM parameters are confirmed to exist [network-stack.ts:100,107; security-stack.ts:189].

`/shared/db/endpoint` is **not** read by CDK — the app reads it at runtime via the instance profile (see below).

#### Import VPC and SG by ID

Use CDK's `.fromLookup()` and `.fromSecurityGroupId()` to import the existing VPC and app-tier SG into this stack's scope. This avoids re-deploying them.

```typescript
const vpc = ec2.Vpc.fromLookup(this, 'SharedVpc', { vpcId });
const appTierSg = ec2.SecurityGroup.fromSecurityGroupId(this, 'AppTierSg', appTierSgId);
```

#### EC2 security group

A new SG for the EC2 instance, separate from `app-tier-sg`. The instance gets both attached.

| Port | Protocol | Source | Why |
|------|----------|--------|-----|
| 22 | TCP | 0.0.0.0/0 | SSH from GitHub Actions (dynamic IP) |
| 80 | TCP | 0.0.0.0/0 | Let's Encrypt HTTP-01 challenge + nginx HTTP→HTTPS redirect |
| 443 | TCP | 0.0.0.0/0 | HTTPS traffic |

**Note:** Port 22 open to the world is acceptable here because access is controlled by the SSH key pair (ed25519 key, private key stored only in GHA secrets). Monitor via CloudTrail / GuardDuty if uncomfortable.

```typescript
const ec2Sg = new ec2.SecurityGroup(this, 'Ec2Sg', {
  vpc,
  description: 'our-adventures EC2 - HTTP, HTTPS, SSH',
  allowAllOutbound: true,
});
ec2Sg.addIngressRule(ec2.Peer.anyIpv4(), ec2.Port.tcp(22),  'SSH from anywhere (GHA deploy)');
ec2Sg.addIngressRule(ec2.Peer.anyIpv4(), ec2.Port.tcp(80),  'HTTP (Certbot challenge + redirect)');
ec2Sg.addIngressRule(ec2.Peer.anyIpv4(), ec2.Port.tcp(443), 'HTTPS');
```

#### IAM instance profile

The instance profile allows the EC2 instance to read SSM parameters at runtime (for `DATABASE_URL`, `GOOGLE_CLIENT_ID`, etc.) and to use SSM Session Manager for ad-hoc access.

```typescript
const instanceRole = new iam.Role(this, 'Ec2Role', {
  assumedBy: new iam.ServicePrincipal('ec2.amazonaws.com'),
  managedPolicies: [
    iam.ManagedPolicy.fromAwsManagedPolicyName('AmazonSSMManagedInstanceCore'),
  ],
});

// Allow reading all /our-adventures/* SSM params (plain strings and SecureStrings)
instanceRole.addToPolicy(new iam.PolicyStatement({
  effect: iam.Effect.ALLOW,
  actions: ['ssm:GetParameter', 'ssm:GetParameters'],
  resources: [
    `arn:aws:ssm:us-east-1:<AWS_ACCOUNT_ID>:parameter/our-adventures/*`,
    `arn:aws:ssm:us-east-1:<AWS_ACCOUNT_ID>:parameter/shared/db/*`,
  ],
}));

// Decrypt SecureString params with the default SSM KMS key
instanceRole.addToPolicy(new iam.PolicyStatement({
  effect: iam.Effect.ALLOW,
  actions: ['kms:Decrypt'],
  resources: [`arn:aws:kms:us-east-1:<AWS_ACCOUNT_ID>:key/alias/aws/ssm`],
}));
```

**Uncertain:** The exact SSM path convention for per-app params (e.g., `/our-adventures/db/password`, `/our-adventures/auth/google-client-id`) is not yet defined in any plan doc. Decide the naming before creating the SSM params. The IAM policy above uses `/our-adventures/*` as a reasonable default.

#### EC2 instance

t4g.nano is ARM (Graviton2). Use `AmazonLinuxCpuType.ARM_64` to get the correct AMI.

```typescript
const instance = new ec2.Instance(this, 'AppServer', {
  vpc,
  vpcSubnets: { subnetType: ec2.SubnetType.PUBLIC },
  instanceType: ec2.InstanceType.of(ec2.InstanceClass.T4G, ec2.InstanceSize.NANO),
  machineImage: ec2.MachineImage.latestAmazonLinux2023({
    cpuType: ec2.AmazonLinuxCpuType.ARM_64,
  }),
  securityGroup: ec2Sg,
  role: instanceRole,
  associatePublicIpAddress: true,
});

// Attach app-tier-sg so the RDS security group allows 5432 from this instance
instance.addSecurityGroup(appTierSg);
```

**Important:** `associatePublicIpAddress: true` gives the instance a public IP, but that IP changes on every stop/start. The Cloudflare DNS record will need updating if the instance is stopped. **Confirmed** from plan: EC2 in public subnet, Cloudflare DNS points to public IP [our-adventures-plan.md:90–102].

**No key pair is defined in CDK.** SSH access during deploy uses an authorized_keys entry, not an EC2 key pair. The GHA deploy key (ed25519 public key) is added to `~/.ssh/authorized_keys` on the instance as a post-deploy manual step (or via user data — see below).

#### GitHubActions-OurAdventures IAM role

This role is assumed by `deploy-infra.yml` (OIDC). Mirrors the `GitHubActions-SharedInfra` pattern exactly [security-stack.ts:154–184], with `sub` scoped to this repo.

```typescript
const ghaRole = new iam.Role(this, 'GitHubActionsRole', {
  roleName: 'GitHubActions-OurAdventures',
  assumedBy: new iam.WebIdentityPrincipal(oidcArn, {
    StringEquals: {
      'token.actions.githubusercontent.com:aud': 'sts.amazonaws.com',
      'token.actions.githubusercontent.com:sub':
        'repo:VietThan/our-adventures:ref:refs/heads/main',
    },
  }),
});

ghaRole.addToPolicy(new iam.PolicyStatement({
  effect: iam.Effect.ALLOW,
  actions: ['sts:AssumeRole'],
  resources: ['arn:aws:iam::<AWS_ACCOUNT_ID>:role/cdk-*'],
}));
```

**Note on `oidcArn`:** `ssm.StringParameter.valueFromLookup()` returns a dummy token at synthesis time and the real value at deploy time. For `WebIdentityPrincipal`, passing a SSM lookup token as the first argument may not resolve correctly in the trust policy. If `cdk synth` shows a dummy ARN like `dummy-value-for-/shared/iam/github-oidc-provider-arn` in the trust policy, switch to reading the value at synthesis with an explicit AWS SDK call or hardcode the ARN after the first deploy.

**Workaround:** After first `cdk synth`, check the `cdk.context.json` file that CDK generates — it caches the resolved SSM values there and uses them on subsequent synths.

#### SSM export: EC2 public IP

Export the instance's public IP to SSM so `deploy-app.yml` can read it without hardcoding.

```typescript
new ssm.StringParameter(this, 'AppServerIp', {
  parameterName: '/our-adventures/ec2/public-ip',
  stringValue: instance.instancePublicIp,
  description: 'our-adventures EC2 public IP (changes on stop/start)',
});
```

**Note:** `instance.instancePublicIp` is a CloudFormation `Ref` token — it resolves to the actual IP after deploy. This means `deploy-app.yml` can do `aws ssm get-parameter --name /our-adventures/ec2/public-ip` to get the current IP dynamically.

### Post-deploy manual steps (not in CDK)

These run once after `cdk deploy`. They are not automated because they require external accounts or one-time setup.

1. **Add SSH deploy key to instance**
   - Generate ed25519 key: `ssh-keygen -t ed25519 -C "our-adventures-deploy" -f ~/.ssh/our-adventures-deploy`
   - Copy public key to EC2: `ssh-copy-id -i ~/.ssh/our-adventures-deploy.pub ec2-user@<public-ip>` (or manually append to `~/.ssh/authorized_keys` on the instance under the `deploy` user)
   - Store private key as GHA secret: `EC2_SSH_PRIVATE_KEY`
   - Store EC2 host as GHA secret or env: `EC2_HOST` (or read from SSM `/our-adventures/ec2/public-ip`)

2. **Create Google OAuth credentials**
   - In Google Cloud Console, create an OAuth 2.0 client
   - Authorized redirect URI: `https://adventures.sleepyshortcake.com/api/auth/callback/google`
   - Store in SSM SecureString:
     - `/our-adventures/auth/google-client-id`
     - `/our-adventures/auth/google-client-secret`
   - Generate `AUTH_SECRET`: `openssl rand -hex 32`
   - Store: `/our-adventures/auth/secret`

3. **Create per-app DB user**
   - Connect to RDS via the EC2 bastion: `psql -h <rds-endpoint> -U postgres -d vietthan`
   - Create user: `CREATE USER our_adventures WITH PASSWORD '...' NOSUPERUSER;`
   - Grant schema access: `GRANT ALL ON SCHEMA our_adventures TO our_adventures;`
   - Store password in SSM: `/our-adventures/db/password`

4. **Create `.env` on EC2** (or populate via deploy workflow)
   - `/home/deploy/app/.env` must contain at minimum:
     ```
     DATABASE_URL=postgresql://our_adventures:<password>@<rds-endpoint>:5432/vietthan?sslmode=require
     NEXTAUTH_URL=https://adventures.sleepyshortcake.com
     NEXTAUTH_SECRET=<auth-secret>
     GOOGLE_CLIENT_ID=<client-id>
     GOOGLE_CLIENT_SECRET=<client-secret>
     ```
   - These values come from SSM. The deploy workflow can populate this file by reading SSM at deploy time.

5. **Cloudflare DNS + Certbot**
   - Add DNS A record: `adventures.sleepyshortcake.com` → EC2 public IP (DNS-only, not proxied, during Certbot issuance)
   - On EC2: `certbot --nginx -d adventures.sleepyshortcake.com` (Certbot modifies the nginx config automatically)
   - After cert is issued, re-enable Cloudflare proxy if desired

### Next.js standalone output (prerequisite)

Before the deploy workflow can work, `next.config.ts` must enable standalone output:

```typescript
// apps/web/next.config.ts
const nextConfig: NextConfig = {
  output: 'standalone',
};
```

With `output: 'standalone'`, `npm run build` produces:
- `.next/standalone/` — self-contained Node.js server (includes only needed `node_modules`)
- `.next/static/` — static assets (must be copied separately)
- `public/` — must be copied separately

The standalone server is started with `node .next/standalone/server.js`, not `next start`. The systemd `ExecStart` in the user data above already uses `node server.js` — this is consistent once the deploy copies files to `/home/deploy/app/`.

**This requires a change to `apps/web/next.config.ts` before the first deploy.**

### `.github/workflows/deploy-app.yml`

Triggers on every push to `main`. Does not use OIDC or AWS credentials — it only needs SSH access to the EC2 instance.

```yaml
name: Deploy app

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: 'npm'
          cache-dependency-path: apps/web/package-lock.json

      - name: Install dependencies
        working-directory: apps/web
        run: npm ci

      - name: Build Next.js (standalone)
        working-directory: apps/web
        run: npm run build

      - name: Set up SSH
        run: |
          mkdir -p ~/.ssh
          echo "${{ secrets.EC2_SSH_PRIVATE_KEY }}" > ~/.ssh/deploy_key
          chmod 600 ~/.ssh/deploy_key
          ssh-keyscan -H "${{ secrets.EC2_HOST }}" >> ~/.ssh/known_hosts

      - name: Rsync build to EC2
        run: |
          rsync -az --delete \
            -e "ssh -i ~/.ssh/deploy_key" \
            apps/web/.next/standalone/ \
            deploy@${{ secrets.EC2_HOST }}:/home/deploy/app/
          rsync -az --delete \
            -e "ssh -i ~/.ssh/deploy_key" \
            apps/web/.next/static/ \
            deploy@${{ secrets.EC2_HOST }}:/home/deploy/app/.next/static/
          rsync -az --delete \
            -e "ssh -i ~/.ssh/deploy_key" \
            apps/web/public/ \
            deploy@${{ secrets.EC2_HOST }}:/home/deploy/app/public/

      - name: Run migrations and restart service
        run: |
          ssh -i ~/.ssh/deploy_key deploy@${{ secrets.EC2_HOST }} << 'ENDSSH'
            set -e
            # Run all migrations idempotently
            psql "$DATABASE_URL" -f /home/deploy/migrations/001_initial_schema.sql
            # Restart Next.js service
            sudo systemctl restart web
          ENDSSH
```

**Required GHA secrets:**

| Secret | Value |
|--------|-------|
| `EC2_SSH_PRIVATE_KEY` | ed25519 private key for the `deploy` user |
| `EC2_HOST` | EC2 public IP or hostname |

**Notes:**
- The `deploy` user needs `sudo systemctl restart web` without a password. Add a sudoers rule on the instance: `deploy ALL=(ALL) NOPASSWD: /bin/systemctl restart web`
- Migration files need to be present on EC2. Either rsync them as part of the deploy (add a step to rsync `db/migrations/` to `/home/deploy/migrations/`) or include them in the standalone output. **Recommended:** add an explicit rsync step for migrations.
- `$DATABASE_URL` must be available in the `deploy` user's environment on EC2. It is read from `/home/deploy/app/.env` which the systemd service's `EnvironmentFile` uses. For the SSH session, either source the env file explicitly or store `DATABASE_URL` in `~/.bashrc` for the `deploy` user.

**Uncertain:** Whether `psql` on the EC2 instance will be in the `deploy` user's `PATH`. Verify after instance setup. May need full path `/usr/bin/psql`.

### `.github/workflows/deploy-infra.yml`

Manual trigger only. Uses OIDC to assume `GitHubActions-OurAdventures`.

```yaml
name: Deploy infra

on:
  workflow_dispatch:

permissions:
  id-token: write   # required for OIDC token request
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS credentials (OIDC)
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::<AWS_ACCOUNT_ID>:role/GitHubActions-OurAdventures
          aws-region: us-east-1

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: 'npm'
          cache-dependency-path: infra/package-lock.json

      - name: Install CDK dependencies
        working-directory: infra
        run: npm ci

      - name: Deploy CDK stack
        working-directory: infra
        run: npx cdk deploy --require-approval never
```

**No GHA secrets needed** — OIDC handles auth. The `role-to-assume` ARN is hardcoded because the role name `GitHubActions-OurAdventures` is stable (explicit `roleName` in CDK).

**`permissions: id-token: write`** is required at the job level for the OIDC token to be requested. This mirrors the pattern used in `shared-aws-infra` [confirmed from security-stack.ts OIDC setup].
