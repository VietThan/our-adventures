## Key decisions made (and why)

### GHA IAM role lives in shared-aws-infra, not our-adventures

`GitHubActions-OurAdventures` is defined in `shared-aws-infra/lib/security-stack.ts`, not in `our-adventures/infra/lib/compute-stack.ts`.

**Why:** chicken-and-egg. If the role were in our-adventures' CDK, `deploy-infra.yml` would need the role to exist before it could deploy — but the role would only exist after a successful deploy. Putting it in shared-aws-infra means the role exists as soon as shared-aws-infra is (re)deployed, and `deploy-infra.yml` can run on day one.

**Implication:** every new app repo that needs a GHA deploy role must add it to `shared-aws-infra/lib/security-stack.ts`.

### Deploy SSH public key via CDK context

The `deploy` user's `authorized_keys` is written during EC2 user data (first boot). The public key is passed to CDK at synth time via `--context deployKeyPublic=...`.

`deploy-infra.yml` reads the key from a GitHub Actions variable (`DEPLOY_KEY_PUBLIC`) and forwards it:

```yaml
run: npx cdk deploy --require-approval never --context "deployKeyPublic=$DEPLOY_KEY_PUBLIC"
```

**Why not SSM:** the GHA role only has permission to assume CDK bootstrap roles — it can't call SSM directly. Embedding in user data via context avoids needing to expand the role's permissions.

**Why not hardcoded:** public keys aren't sensitive, but hardcoding any value that could change (key rotation) in source is bad practice.

### cdk.context.json is gitignored

CDK caches SSM lookups (VPC ID, SG ID) in `cdk.context.json`. This file contains the AWS account ID embedded in lookup keys. It's gitignored to prevent accidental exposure in this public repo.

**Implication:** every local CDK synth or deploy that needs lookup values must be run with valid AWS credentials so CDK can repopulate the cache. CI always has credentials, so this is only relevant for local development.

### No aws-cdk CLI in package.json

`aws-cdk` (the CLI) is invoked via `npx cdk` rather than being listed in `devDependencies`. This matches the `shared-aws-infra` pattern and avoids version confusion between `aws-cdk` (CLI, version scheme `2.1118.x`) and `aws-cdk-lib` (library, version scheme `2.250.x`).

## Deployment sequence (first time)

1. **shared-aws-infra** — already deployed before this work began. Updated 2026-04-24 to add `GitHubActions-OurAdventures` OIDC role.

2. **GitHub Actions variables/secrets** — set before running deploy-infra:
   - `AWS_DEPLOY_ROLE_ARN` (variable) — ARN of `GitHubActions-OurAdventures`
   - `DEPLOY_KEY_PUBLIC` (variable) — ed25519 public key for the `deploy` user
   - `EC2_SSH_PRIVATE_KEY` (secret) — corresponding private key
   - `EC2_HOST` (variable) — EC2 public IP, set after first infra deploy

3. **deploy-infra.yml** — manual trigger. Provisions EC2, writes public IP to SSM `/our-adventures/ec2/public-ip`.

4. **deploy-app.yml** — triggers on push to main. Requires EC2 to be running and `EC2_HOST` set.

## Manual one-time setup steps

These are not automated — run once after first infra deploy.

### 1. Create the `our_adventures` DB user

RDS is in a private subnet — connect via SSM port forwarding (see `shared-aws-infra/docs/connecting-to-rds.md`), then run in DBeaver or psql against the `vietthan` database:

```sql
CREATE USER our_adventures WITH PASSWORD '<password>';
GRANT CONNECT ON DATABASE vietthan TO our_adventures;
```

The schema and tables are created automatically by `db/migrations/001_initial_schema.sql` on first `deploy-app.yml` run — no manual migration needed.

### 2. Store secrets in SSM

```bash
# DB password (must match what you used in CREATE USER above)
aws ssm put-parameter --name /our-adventures/db/password --value "..." --type SecureString

# Google OAuth (from Google Cloud Console)
aws ssm put-parameter --name /our-adventures/auth/google-client-id --value "..." --type SecureString
aws ssm put-parameter --name /our-adventures/auth/google-client-secret --value "..." --type SecureString

# Auth.js secret (random string)
aws ssm put-parameter --name /our-adventures/auth/secret --value "$(openssl rand -base64 32)" --type SecureString
```

### 3. Point Cloudflare DNS at EC2

Get the IP: `aws ssm get-parameter --name /our-adventures/ec2/public-ip --query 'Parameter.Value' --output text`

Add an A record for `adventures.sleepyshortcake.com` pointing at that IP.

### 4. Provision TLS certificate (Certbot)

SSH into the instance and run:

```bash
sudo certbot --nginx -d adventures.sleepyshortcake.com
```
