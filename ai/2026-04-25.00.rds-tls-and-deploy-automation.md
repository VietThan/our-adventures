### Instance replacement mechanics

Changing `UserData` on an EBS-backed `AWS::EC2::Instance` does **not** reliably
recreate the instance — CloudFormation can stop and restart it, but user data
only runs on first launch. To get a fresh instance with the new user data, force
replacement in CDK by setting `userDataCausesReplacement: true` on the
`ec2.Instance`.

Do **not** rely on manually terminating the EC2 instance and then running
`cdk deploy` again. A no-op CloudFormation update can leave the stack pointing at
the terminated physical instance instead of recreating it.

### Downtime during instance replacement

This plan accepts brief downtime (~5–15 minutes) during instance replacement. The timeline:

1. `cdk deploy ComputeStack` replaces the old instance → DNS still points to the old IP → **site is down**
2. New instance boots, runs user data (CA bundle, Certbot, nginx)
3. You update the `EC2_HOST` GHA variable and push to `main`
4. `deploy-app.yml` deploys code, app passes readiness check, DNS is updated → **site is back**

This is acceptable for a 2-user personal app. To minimize the window: have the
branch ready to push before running the replacement deploy, and update `EC2_HOST`
immediately after the new instance is running.

## 1. RDS TLS — why it matters

The Next.js app connects to RDS with `ssl: { rejectUnauthorized: false }` (`apps/web/src/db/client.ts:17`). This encrypts traffic but accepts any certificate — a MITM between EC2 and RDS could present a forged cert. The `psql` migration step in the deploy workflow has the same gap: no explicit `sslmode` or CA reference, so it defaults to `sslmode=prefer`.

---

## 2. Deploy automation — why it matters

Today, replacing the EC2 instance requires three manual steps after `cdk deploy`: update the Cloudflare A record, SSH in, run Certbot. This plan automates two of those:

- **Certbot** runs automatically in user data (DNS-01 challenge — does not require the A record to point at the new instance)
- **Cloudflare A record** is updated by `deploy-app.yml` after the app is deployed and running, avoiding a 502 window

One manual step remains: updating the `EC2_HOST` GHA variable so the deploy workflow can SSH to the new instance. This could be automated later by having the workflow read `/our-adventures/ec2/public-ip` from SSM (requires adding OIDC credentials to `deploy-app.yml`), but that's out of scope here.

---

## IPv6 — investigated, deferred

We investigated dropping public IPv4 in favor of IPv6-only to save $3.60/month. Two blockers:

1. **Cloudflare proxy + IPv6-only origin is unreliable.** The official docs say Cloudflare "prefers IPv4" when connecting to origins. Community reports of 522 errors with AAAA-only proxied records span 2021–2025. The docs don't explicitly confirm IPv6-only origin support. ([Cloudflare IPv6 compatibility docs](https://developers.cloudflare.com/network/ipv6-compatibility/))

2. **GHA hosted runners lack IPv6 outbound.** `ubuntu-latest` runners cannot SSH to IPv6 addresses. The [open GitHub issue](https://github.com/actions/runner-images/issues/668) confirms this. The ARC 0.13.0 release (2025-10-16) added dual-stack, but only for self-hosted K8s runners.

Revisit when either: (a) Cloudflare explicitly supports IPv6-only origins with proxy, or (b) we migrate deploys from SSH to SSM (which sidesteps the GHA IPv6 issue).

## Known oddity: KMS alias ARN in compute-stack.ts

The IAM policy at `compute-stack.ts:84-88` uses `arn:aws:kms:...:key/alias/aws/ssm` as the resource for `kms:Decrypt`. This ARN format is malformed — `key/` expects a key ID, not an alias. The correct alias ARN would be `arn:aws:kms:...:alias/aws/ssm`, but alias ARNs cannot be used in IAM `Resource` elements for `kms:Decrypt` anyway.

Production works because the AWS-managed `aws/ssm` key has a key policy that grants decrypt to any IAM principal in the account with SSM permissions. The IAM statement is likely a no-op.

This plan does not change it — the new Cloudflare SSM SecureString will decrypt via the same key policy path that existing secrets use. Fixing the ARN is a separate cleanup.

### Step 1: Update compute-stack.ts user data

Add to user data in `infra/lib/compute-stack.ts`, after the existing `postgresql15` install block.

**Important:** The existing user data starts with `set -euxo pipefail` (`compute-stack.ts:119`). The `-x` flag echoes every command to `/var/log/cloud-init-output.log`, which would leak the Cloudflare API token. Disable xtrace around secret retrieval:

```bash
# AWS RDS CA bundle for TLS verification
curl -fsSL -o /etc/ssl/certs/rds-combined-ca-bundle.pem \
  https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem
chmod 644 /etc/ssl/certs/rds-combined-ca-bundle.pem

# Certbot + Cloudflare DNS plugin (venv because AL2023 doesn't package them)
# AL2023 ships Python 3.9 as default, but 3.12 is in the base repo.
# Certbot is dropping 3.9 support — use 3.12 (supported until Oct 2028).
dnf install -y python3.12
python3.12 -m venv /opt/certbot
/opt/certbot/bin/pip install certbot certbot-dns-cloudflare certbot-nginx
ln -sf /opt/certbot/bin/certbot /usr/bin/certbot

# Pull the Cloudflare API token from SSM and write the credentials file.
# Disable xtrace to avoid leaking the token into cloud-init-output.log.
set +x
CF_TOKEN=$(aws ssm get-parameter \
  --name /our-adventures/cloudflare/dns-api-token \
  --with-decryption \
  --query Parameter.Value \
  --output text \
  --region us-east-1)
mkdir -p /etc/letsencrypt
printf 'dns_cloudflare_api_token = %s\n' "$CF_TOKEN" > /etc/letsencrypt/cloudflare.ini
chmod 600 /etc/letsencrypt/cloudflare.ini
unset CF_TOKEN
set -x

# Provision TLS certificate (non-interactive, DNS-01 challenge).
# DNS-01 does not require the A record to point at this instance —
# it proves ownership via a TXT record. The A record is updated later
# by deploy-app.yml after the app is deployed and running.
certbot certonly \
  --dns-cloudflare \
  --dns-cloudflare-credentials /etc/letsencrypt/cloudflare.ini \
  --non-interactive \
  --agree-tos \
  --email vietthan@gmail.com \
  -d adventures.sleepyshortcake.com

# Write the nginx HTTPS config now that the cert exists
# (replaces the HTTP-only config written earlier in user data)
cat > /etc/nginx/conf.d/our-adventures.conf << 'NGINXEOF'
server {
    listen 80;
    server_name adventures.sleepyshortcake.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name adventures.sleepyshortcake.com;

    ssl_certificate /etc/letsencrypt/live/adventures.sleepyshortcake.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/adventures.sleepyshortcake.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
NGINXEOF

systemctl restart nginx

# Set up auto-renewal timer
cat > /etc/systemd/system/certbot-renew.timer << 'TIMEREOF'
[Unit]
Description=Certbot renewal timer

[Timer]
OnCalendar=*-*-* 02:30:00
RandomizedDelaySec=3600
Persistent=true

[Install]
WantedBy=timers.target
TIMEREOF

cat > /etc/systemd/system/certbot-renew.service << 'SVCEOF'
[Unit]
Description=Certbot renewal

[Service]
Type=oneshot
ExecStart=/usr/bin/certbot renew --quiet --deploy-hook "systemctl restart nginx"
SVCEOF

systemctl daemon-reload
systemctl enable certbot-renew.timer
systemctl start certbot-renew.timer
```

Note: user data does NOT update the Cloudflare A record. DNS continues pointing to the old instance until the deploy workflow cuts it over after the app is running. This avoids a 502 window.

### Step 2: Update the Next.js database client

In `apps/web/src/db/client.ts`, replace the `rejectUnauthorized: false` workaround:

```ts
import { readFileSync } from "node:fs";

const RDS_CA_PATH = "/etc/ssl/certs/rds-combined-ca-bundle.pem";

function buildSslConfig(hostname: string | null) {
  if (!shouldUseSsl(hostname)) return undefined;

  try {
    return { ca: readFileSync(RDS_CA_PATH, "utf8") };
  } catch {
    // CA bundle not found — likely local dev hitting a non-localhost PG.
    // Fall back to unverified TLS rather than crashing, but log a warning.
    console.warn(`RDS CA bundle not found at ${RDS_CA_PATH} — using unverified TLS`);
    return { rejectUnauthorized: false };
  }
}
```

Use `buildSslConfig(hostname)` instead of the current inline object in `getPool()`.

The fallback keeps the app functional if someone runs it against a remote Postgres without the CA file installed. In production the file will always exist.

### Step 3: Update the deploy workflow

In `.github/workflows/deploy-app.yml`:

**a) psql connection — add verified TLS:**

```bash
DATABASE_URL="postgresql://our_adventures:${DB_PASS}@${DB_ENDPOINT}:5432/vietthan?sslmode=verify-full&sslrootcert=/etc/ssl/certs/rds-combined-ca-bundle.pem"
```

**b) Cloudflare DNS update — add after `sudo systemctl restart web`:**

At the end of the on-instance SSH block, after the web service restart, add a readiness check and then the Cloudflare A record update. This runs on the instance (which has the Cloudflare token), and only after the app is confirmed healthy:

```bash
# Wait for the app to be ready before cutting DNS over.
# systemctl restart can return before the process is actually serving.
echo "Waiting for app readiness..."
for i in $(seq 1 30); do
  if systemctl is-active --quiet web && curl -fsS -o /dev/null http://127.0.0.1:3000/; then
    echo "App is ready after ${i}s"
    break
  fi
  if [ "$i" -eq 30 ]; then
    echo "ERROR: App did not become ready within 30s" >&2
    exit 1
  fi
  sleep 1
done

# Update Cloudflare A record to point to this instance.
# Runs after readiness check to avoid a 502 window.
# The deploy-app.yml SSH block starts with set -e only (no xtrace),
# so set +x here is just a safety guard against future changes.
set +x

CF_TOKEN=$(aws ssm get-parameter \
  --name /our-adventures/cloudflare/dns-api-token \
  --with-decryption \
  --query Parameter.Value \
  --output text \
  --region us-east-1)

CF_ZONE_ID=$(aws ssm get-parameter \
  --name /our-adventures/cloudflare/zone-id \
  --query Parameter.Value \
  --output text \
  --region us-east-1)

IMDS_TOKEN=$(curl -sX PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
PUBLIC_IP=$(curl -s -H "X-aws-ec2-metadata-token: $IMDS_TOKEN" \
  http://169.254.169.254/latest/meta-data/public-ipv4)

# Find the existing A record ID for adventures.sleepyshortcake.com
CF_RESPONSE=$(curl -fsS -X GET \
  "https://api.cloudflare.com/client/v4/zones/${CF_ZONE_ID}/dns_records?type=A&name=adventures.sleepyshortcake.com" \
  -H "Authorization: Bearer ${CF_TOKEN}" \
  -H "Content-Type: application/json")

CF_SUCCESS=$(echo "$CF_RESPONSE" | python3 -c "import sys,json; print(json.load(sys.stdin).get('success', False))")
if [ "$CF_SUCCESS" != "True" ]; then
  echo "ERROR: Cloudflare API list request failed" >&2
  echo "$CF_RESPONSE" >&2
  exit 1
fi

CF_RECORD_ID=$(echo "$CF_RESPONSE" | python3 -c "import sys,json; r=json.load(sys.stdin)['result']; print(r[0]['id'] if r else '')")

if [ -n "$CF_RECORD_ID" ]; then
  # Update existing record
  CF_UPDATE=$(curl -fsS -X PUT \
    "https://api.cloudflare.com/client/v4/zones/${CF_ZONE_ID}/dns_records/${CF_RECORD_ID}" \
    -H "Authorization: Bearer ${CF_TOKEN}" \
    -H "Content-Type: application/json" \
    --data "{\"type\":\"A\",\"name\":\"adventures\",\"content\":\"${PUBLIC_IP}\",\"proxied\":true}")
  CF_OK=$(echo "$CF_UPDATE" | python3 -c "import sys,json; print(json.load(sys.stdin).get('success', False))")
  if [ "$CF_OK" != "True" ]; then
    echo "ERROR: Cloudflare API update failed" >&2
    echo "$CF_UPDATE" >&2
    exit 1
  fi
  echo "Cloudflare A record updated to ${PUBLIC_IP}"
else
  # Create new record
  CF_CREATE=$(curl -fsS -X POST \
    "https://api.cloudflare.com/client/v4/zones/${CF_ZONE_ID}/dns_records" \
    -H "Authorization: Bearer ${CF_TOKEN}" \
    -H "Content-Type: application/json" \
    --data "{\"type\":\"A\",\"name\":\"adventures\",\"content\":\"${PUBLIC_IP}\",\"proxied\":true}")
  CF_OK=$(echo "$CF_CREATE" | python3 -c "import sys,json; print(json.load(sys.stdin).get('success', False))")
  if [ "$CF_OK" != "True" ]; then
    echo "ERROR: Cloudflare API create failed" >&2
    echo "$CF_CREATE" >&2
    exit 1
  fi
  echo "Cloudflare A record created for ${PUBLIC_IP}"
fi
```

Note: the Cloudflare DNS update runs on every deploy, not just instance replacements. This is harmless — if the IP hasn't changed, it's a no-op update. It also means a stop/start (which changes the public IP) is automatically fixed on the next deploy.

## Rollback

**If Cloudflare API update fails in deploy-app.yml:**
- The deploy workflow will fail loudly (the Cloudflare block checks `.success` and exits non-zero on failure)
- Update the A record manually in the Cloudflare dashboard, same as today
- App is already deployed and running — only DNS is affected

**If Certbot fails in user data:**
- SSH in (or SSM Session Manager) and run Certbot manually, same as today
- Debug the user data script in `/var/log/cloud-init-output.log`

**If RDS TLS verification fails:**
- The `buildSslConfig` fallback degrades to `rejectUnauthorized: false` with a warning — app stays up
- To fully revert: restore the old client.ts and remove `sslmode` from deploy-app.yml
