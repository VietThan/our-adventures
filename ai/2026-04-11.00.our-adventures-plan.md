# Plan: our-adventures — Full-Stack Couples' Adventure Tracker

**Date:** 2026-04-11  
**Status:** Draft  
**Repo:** `VietThan/our-adventures` (submodule alongside `nyc-adventure`)

---

## Context

`nyc-adventure` is a frontend-only proof-of-concept Linh built: a single HTML file with all state in `localStorage`. It has great UX instincts (category wheel, surprise picker, seasonal tags, mark done + rate) but state doesn't sync between devices and can't be shared between Viet and Linh. This project makes it real — persisted, synced, and owned by both.

---

## Core Requirements

- Shared state: what Viet marks done, Linh sees immediately (and vice versa)
- Data persists across devices and browsers
- Preserve all UX ideas from `nyc-adventure` (categories, wheel nav, picker, ratings, seasons)
- Seed from the existing 400 activities; add/edit/delete new ones
- Private — just the two of them
- AWS as cloud provider

---

## Key Decisions

### Auth
**Auth.js (NextAuth v5) with Google provider** — Google OAuth in ~10 lines of config, session stored as a signed JWT cookie (strategy: `"jwt"`), allowlist enforced in the `signIn` callback against the two known emails. No AWS auth service needed.

Auth.js requires server-side routes (`/api/auth/*`) to handle the OAuth callback, which means Next.js runs in **server mode** (not static export) — see Hosting below.

Authenticated server work stays inside the Next.js app. Route handlers and server code use the Auth.js session directly, so there is no second backend service that has to re-verify shared cookies across process boundaries.

### Frontend
**Next.js (App Router, server mode)** — React ecosystem, TypeScript, Tailwind. Runs as a Node.js process on EC2 (not a static export). Auth.js integrates natively with App Router.

### Backend
**Next.js server-side routes and actions on EC2 t4g.nano** — one always-on Node.js process serves both the UI and backend endpoints. Database access lives in the Next.js app, which removes the need for a separate API service, shared auth verification between services, and cross-process deploy orchestration. Managed by CDK (EC2 instance + Security Groups + IAM instance profile).

Deployed via **GitHub Actions**: on push to `main`, GHA builds the Next.js app, rsyncs the artifact to the instance over SSH, runs migrations, and restarts the web systemd service. No CodeDeploy agent needed.

### Database
**PostgreSQL on AWS RDS** — relational model is the right fit for this data (activities, completions, users have real foreign-key relationships). Use a shared database named `vietthan`, with `our_adventures` isolated as its own PostgreSQL schema. Run this on `db.t4g.micro` with a single-AZ RDS instance — simple, cheap (~$14–16/month), no Aurora overhead for a 2-user app. Managed by CDK. Migrations run as a deploy step from the repo-level `db/` contract.

RDS sits in a private subnet; only the EC2 instance's Security Group is allowed to connect on port 5432. No public exposure.

**Security & backups:**
- Enable **storage encryption** (RDS default KMS key is fine).
- Connection string must use `sslmode=require` (the Next.js database client enforces TLS to RDS).
- Automated backups: 7-day retention (RDS default).
- Manual snapshot before any major data migration or Phase 3 feature launch.

### Local Development
**Docker Compose** — a `docker-compose.yml` at the repo root spins up a local Postgres container on port `5432`, matching the production version. Running the Next.js app locally connects to this container via `DATABASE_URL` in a `.env.local` file. The shared database is `vietthan`, and this app owns the `our_adventures` schema within it. Schema migrations run against it the same way as in production, and baseline activity data is loaded separately from the canonical seed file.

```yaml
# docker-compose.yml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: vietthan
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
volumes:
  pgdata:
```

`docker compose down -v` wipes the volume for a clean slate. No local Postgres install needed.

### Infrastructure-as-Code
**AWS CDK (TypeScript)** — provisions VPC, RDS, EC2 instance, Security Groups. No S3/CloudFront stack, no auth stack. CDK is run manually (or via a dedicated GHA workflow) when infra changes. Day-to-day deploys do not touch CDK.

### CI/CD
**GitHub Actions** — two workflows:

| Workflow | Trigger | What it does |
|---|---|---|
| `deploy-app.yml` | push to `main` | Build the Next.js app, rsync to EC2, run migrations, restart the web service |
| `deploy-infra.yml` | manual trigger only | `cdk deploy` for infra changes |

GHA authenticates to EC2 via an SSH deploy key (private key stored as GHA secret). **Future:** consider GitHub's OIDC provider + AWS STS `AssumeRole` for better key hygiene (no long-lived keys). For now, SSH key with 6-month rotation policy and immediate revocation if leaked.

No AWS OIDC needed for deploys since GitHub Actions can push the build artifacts directly to the EC2 instance over SSH.

### Hosting
**EC2 — nginx reverse proxy** — one Next.js app runs on EC2 t4g.nano as a systemd service:
- Next.js server on port `3000`
- nginx listens on port `80` (dev/test only) and proxies all traffic to Next.js
- **HTTPS (port 443) required for production** — JWT cookies must be sent over TLS. Use `adventures.sleepyshortcake.com` as the canonical host, create a Cloudflare DNS record pointing at the EC2 public IP, and provision TLS on the instance with Certbot + Let's Encrypt before enabling Google OAuth for regular use.

No S3 or CloudFront needed. `adventures.sleepyshortcake.com` is the public entry point.

### Domain
Use `adventures.sleepyshortcake.com` under the existing Cloudflare-managed `sleepyshortcake.com` zone.

Setup:
- Create a DNS record in Cloudflare for `adventures.sleepyshortcake.com` pointing to the EC2 public IP
- Keep DNS-only mode during initial Certbot issuance to avoid proxy-related confusion
- Set `NEXTAUTH_URL=https://adventures.sleepyshortcake.com`
- Register `https://adventures.sleepyshortcake.com/api/auth/callback/google` in the Google OAuth client
- Configure nginx to redirect `http://adventures.sleepyshortcake.com` to HTTPS after the certificate is in place

## Data Model (PostgreSQL)

**Bootstrap strategy:**
- `db/migrations/` owns schema only: creation of `our_adventures` plus its tables, indexes, and constraints
- `data/activities.json` is the canonical baseline dataset ported from `nyc-adventure`
- A one-time import path loads that baseline data into a fresh database; this can be a SQL seed file or a small import script, but it is not part of the recurring migration chain
- Production DB dumps are for backup, restore, or debugging local issues against real data, not for normal project bootstrap
- Categories are part of the DB contract and should be validated strictly in the schema
- Seasons stay flexible for now; preserve the source values but defer stricter normalization until the product proves it needs it

```sql
CREATE SCHEMA IF NOT EXISTS our_adventures;

CREATE TYPE our_adventures.activity_category AS ENUM (
  'cinema',
  'food',
  'bakery',
  'arts',
  'shows',
  'explore',
  'wellness',
  'daytrip',
  'free',
  'classes'
);

-- Seeded from nyc-adventure; custom ones added by users
CREATE TABLE our_adventures.activities (
  id          SERIAL PRIMARY KEY,
  title       TEXT        NOT NULL,
  category    our_adventures.activity_category NOT NULL,
  season      TEXT        NOT NULL,   -- preserve current source values; normalize later if needed
  notes       TEXT,                   -- personal commentary
  tip         TEXT,                   -- practical info (address, price, how to get there)
  is_custom   BOOLEAN     NOT NULL DEFAULT FALSE,
  added_by    TEXT,                   -- Google sub of creator (from Auth.js); NULL for seeded data
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- One row per Auth.js user (auto-created on first login)
CREATE TABLE our_adventures.users (
  id           TEXT        PRIMARY KEY,  -- Google account sub (stable, from Auth.js account.providerAccountId)
  email        TEXT        NOT NULL UNIQUE,
  display_name TEXT        NOT NULL,
  avatar_url   TEXT,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Each person's completion of an activity is independent
CREATE TABLE our_adventures.completions (
  activity_id  INT         NOT NULL REFERENCES our_adventures.activities(id) ON DELETE CASCADE,
  user_id      TEXT        NOT NULL REFERENCES our_adventures.users(id),
  completed_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  rating       SMALLINT    CHECK (rating BETWEEN 1 AND 5),
  review       TEXT,
  PRIMARY KEY (activity_id, user_id)
);

CREATE INDEX ON our_adventures.activities (category);
CREATE INDEX ON our_adventures.completions (user_id);
```

**Key query patterns:**
- List by category → `WHERE category = $1 ORDER BY id`
- Activity with both users' status → LEFT JOIN completions twice (once per user id)
- All completions for a user → `WHERE user_id = $1`
- Random undone activity → `WHERE id NOT IN (SELECT activity_id FROM completions WHERE user_id = $1) ORDER BY RANDOM() LIMIT 1`

**Category ownership:**
- The database owns the canonical category keys
- The frontend owns labels, ordering, and color presentation for those keys
- Adding a new category requires a schema migration

## API Surface

All server endpoints live inside the Next.js app as route handlers under `/api/*`, protected by Auth.js session checks in server-side code.

**Transaction safety:** The `/activities/:id/complete` endpoint is idempotent (upsert on `(activity_id, user_id)` primary key), so no special transaction handling needed. Both users can independently mark the same activity done without conflicts.

| Method | Path | Description |
|---|---|---|
| `GET` | `/activities` | List all activities (optional `?category=` filter) |
| `GET` | `/activities/:id` | Get single activity with both users' completion status |
| `POST` | `/activities` | Create a custom activity |
| `PUT` | `/activities/:id` | Update a custom activity (own only) |
| `DELETE` | `/activities/:id` | Delete a custom activity (own only) |
| `POST` | `/activities/:id/complete` | Mark done + optional rating |
| `DELETE` | `/activities/:id/complete` | Unmark |
| `GET` | `/activities/pick` | Surprise picker — returns random undone activity, optional `?category=` |
| `GET` | `/me` | Current user profile |
